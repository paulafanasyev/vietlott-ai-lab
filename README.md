# Vietlott AI Lab

Исследовательская система для Vietlott Mega 6/45 и Power 6/55: сбор результатов из первоисточников,
неизменяемая история, прогнозы разными методами и честное сравнение со случайным выбором.
Интерфейс и отчёты — на вьетнамском языке; техническая документация для разработчика — на русском.

> Лотерея случайна. Система не обещает выигрыш; её задача — измерять, а не угадывать.

## Статус

| Этап | Что | Статус |
|---|---|---|
| 1 | Источники, база, сверка, статусы, автоматический сбор, журнал задач, бэкап и проверка восстановления, экспорт | код готов; юнит-тесты (без базы) проходят; тесты на PostgreSQL, реальные источники и бэкап ещё НЕ запускались — PENDING до CI и Neon. Подробно: `docs/acceptance-stage1.md` |
| 2–6 | Прогнозы, бэктест, самообучение, интерфейс | не начато |

## Структура

- `db/migrations/` — схема PostgreSQL. История только дописывается: UPDATE/DELETE/TRUNCATE запрещены
  триггерами, цепочка хешей ловит подмену в обход триггеров (`python -m vlab verify`).
- `worker/` — Python: сбор (`vlab/sources`), сверка (`vlab/reconcile.py`), запись (`vlab/store.py`),
  расписание тиражей (`vlab/schedule.py`), CLI (`python -m vlab migrate|ingest|checkpoint|verify|export|record-backup`).
- `docs/workflows/` — файлы GitHub Actions. Агент не может писать в `.github/workflows`, их нужно
  скопировать вручную.

## Источники и статусы

| Источник | Роль |
|---|---|
| vietlott.vn (AjaxPro, список результатов) | официальный; страница бывает устаревшей, сервер может не пускать зарубежные IP |
| pqminh-4/vietlott-data | архив (полный, сам сверяется с Vietlott) |
| vietvudanh/vietlott-data | архив (нет Mega 00001–00197) |
| NhanAZ-Data/vietlott-research | архив (новые тиражи частично с Minh Ngọc) |

VERIFIED = официальный источник совпал хотя бы с одним архивом. CROSS-CHECKED = совпали 2+ архива.
NOT PROVEN = только одна группа происхождения (архивы-копии друг друга считаются одним подтверждением). CONFLICT = источники расходятся (тираж исключается из расчётов).
PENDING = по расписанию тираж прошёл, данных ещё нет.

## Запуск (один раз, делает Павел)

1. Создать бесплатную базу на [Neon](https://neon.tech) и скопировать строку подключения владельца.
2. В SQL-консоли Neon после первого `migrate` создать пользователя для воркера:
   `CREATE ROLE vlab_worker LOGIN PASSWORD '<пароль>' IN ROLE vlab_app;`
3. Создать пустой ПРИВАТНЫЙ репозиторий для бэкапов (например `vietlott-ai-lab-backups`) и fine-grained token
   с правом Contents: read/write только на него.
4. В репозитории → Settings → Secrets → Actions добавить `DATABASE_URL` (владелец), `DATABASE_URL_WORKER`
   (vlab_worker), `BACKUP_REPO` (`владелец/имя`), `BACKUP_REPO_TOKEN`.
5. Скопировать `docs/workflows/ci.yml`, `ingest.yml`, `backup.yml` в `.github/workflows/`.
6. Actions → ci, затем ingest, затем backup → Run workflow. Ссылки на запуски — в `docs/acceptance-stage1.md`.

## Тесты

```bash
cd worker && pip install -e ".[dev]" && pytest -v
# с базой: TEST_DATABASE_URL=postgresql://... pytest -v
```

## Гарантии, которые проверяют тесты

- Номер, однажды ставший VERIFIED, автоматическая задача не может заменить другим: только CONFLICT.
  Сменить его может лишь роль `vlab_admin` (это проверяет сама база, не только код).
- Каждое обращение к источнику (даже неудачное) пишется отдельным соединением и переживает откат задачи.
- Редиректы проверяются на каждом шаге, ответ ограничен 25 МБ, Retry-After — не больше 300 с.
- Контрольные точки всех таблиц истории (число строк, max id, хеш содержимого) ловят даже удаление
  последней строки; копия контрольной точки лежит в приватном репозитории бэкапов.
- Роль воркера может только дописывать таблицы этапа 1; конфликты разрешает и настройки меняет только `vlab_admin`.
- Две одновременные загрузки не пересекаются (advisory lock), миграции тоже.
- PENDING ставится только следующему тиражу после последнего известного (праздники не сдвигают номера).
